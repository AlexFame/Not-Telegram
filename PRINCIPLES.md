# PRINCIPLES — инженерные и продуктовые принципы

Мета-слой над [VISION.md](VISION.md), [DESIGN.md](DESIGN.md), [ARCHITECTURE.md](ARCHITECTURE.md), [CODING.md](CODING.md), [PRODUCT.md](PRODUCT.md). Это общий словарь и инструментарий — не чек-лист «применить всё».

---

## Главное правило (выше всего списка)

> **Не применяй паттерн только потому, что он существует. Применяй, только когда он делает систему проще.**

Паттерн, добавляющий слой без реальной второй точки использования, — это техдолг под видом «правильной архитектуры». По умолчанию — самое простое решение (KISS), а абстракцию вводим по факту нужды (YAGNI), а не заранее.

---

## Приоритет при конфликте принципов

Когда принципы противоречат друг другу — решаем в этом порядке:

1. **Пользовательский опыт (UX)**
2. **Простота**
3. **Надёжность**
4. **Масштабируемость**
5. **Производительность**
6. **Красота кода**

Красота кода уступает простоте; простота уступает UX. Если «чистый паттерн» ухудшает UX или усложняет — он проигрывает.

## Гейт перед каждым архитектурным или UX-решением

1. Можно ли сделать проще?
2. Можно ли убрать этот экран?
3. Можно ли убрать этот шаг?
4. Можно ли убрать эту кнопку?
5. Масштабируется ли решение?
6. Не создаёт ли оно технический долг?
7. Соответствует ли философии Apple?
8. Соответствует ли философии нашего продукта ([VISION.md](VISION.md))?
9. Будет ли это казаться правильным через 10 лет?

## Что применяем СЕЙЧАС (в прототипе)

Минимальный набор, который реально упрощает систему на текущем этапе:

| Принцип / паттерн | Зачем именно сейчас |
|---|---|
| KISS, YAGNI, DRY | Базовая дисциплина против переусложнения. |
| SRP, Separation of Concerns | Слои View / ViewModel / Domain / Data (см. ARCHITECTURE). |
| Clean Architecture (лёгкая), MVVM | Однонаправленный поток, тестируемый домен. |
| SSOT | Карточка — единый источник правды; живая ссылка, не копия. |
| Composition over Inheritance | Полиморфизм карточки — композиция поведения, не наследование. |
| Protocol-Oriented + DI/IoC | Репозитории за протоколами → прототипное локальное хранилище меняется на сеть без правок домена. |
| Value-Oriented Programming | `struct`/`enum` по умолчанию; недопустимые состояния непредставимы. |
| Repository / Service Layer | Доступ к данным изолирован. |
| Modular / Feature-based | Модули Chats / Cards / Deals / Search / Content / Profile. |
| Async/Await, Structured Concurrency | Нативная многозадачность. |
| Offline-first, Caching, Lazy Loading | Кэш-снимок карточки для офлайна; ленивая лента. |
| **UX-законы:** Hick, Fitts, Miller, Jakob, Tesler, Doherty, Occam, Least Astonishment | Прямо обслуживают «тупого и ленивого»: меньше выбора, крупные цели, знакомые паттерны, мгновенный отклик. |
| Progressive Disclosure, Recognition over Recall, Error Prevention, Feedback, Consistency, Content First, Motion with Purpose, Accessibility First, Privacy by Design, Security by Design | Ядро DESIGN. |
| **Продукт:** JTBD, First Principles, MVP Thinking, Pareto (80/20) | Прототип решает один Job, проверяет одну гипотезу. |

## К чему тянемся ПОЗЖЕ — только по реальной нужде

Не вводим, пока конкретная боль не появится. Держим в словаре, чтобы узнать момент:

- **Coordinator Pattern** — когда навигация перерастёт `NavigationStack` (много потоков, deep links). До этого — избыточен.
- **Strategy / State / Command / Factory / Observer** — точечно, когда ветвление/состояния станут болью. Не раскладывать заранее.
- **CQRS** — только если модель чтения/записи реально разъедется.
- **Event-driven architecture, Eventual Consistency** — только с реальной синхронизацией между устройствами/сервером.
- **Optimistic UI** — когда появится сеть с ощутимой задержкой.
- **Pagination, Virtualization** — когда списки вырастут настолько, что ленивая загрузка перестанет справляться.
- **Repository → сетевые реализации, Background Tasks** — при переходе от локального прототипа к бэкенду.

Правило перехода: паттерн из этого раздела попадает в «сейчас» только когда на него есть **вторая реальная точка использования** или измеримая боль — не «на будущее».

## Качество как фон (всегда, не как фичи)

Readability over Cleverness · Testability · Maintainability · Scalability · Extensibility · Reliability · Security by Design · Privacy by Design · Accessibility First.

Эти свойства не «включаются» — они следствие соблюдения принципов выше и приоритета из раздела о конфликтах.
