# ARCHITECTURE — архитектура SwiftUI и проекта

Реализует [VISION.md](VISION.md), следуя [PRINCIPLES.md](PRINCIPLES.md) (паттерны — только когда упрощают). Цель — система, которую можно развивать годами: минимальная связанность, максимальная расширяемость, лёгкая тестируемость, без техдолга. Простое решение всегда предпочтительнее сложного.

---

## 1. Платформа: нативный SwiftUI, iOS

Уровень Apple — сочность, 60/120 fps, «правильные» анимации — **нельзя подделать** на webview / React Native / Flutter. Поэтому:

> Пишем нативно на **Swift + SwiftUI**. Любой вопрос «а давай через кроссплатформу/вебвью» — сразу нет.

Целимся в современный iOS (SwiftUI-first, `@Observable`, `NavigationStack`, `async/await`).

---

## 2. Разделение слоёв

Однонаправленный поток данных. UI не знает о хранилище, домен не знает о UI.

```
View (SwiftUI)  →  ViewModel (@Observable)  →  Domain (use cases, бизнес-логика)
                                                   ↓
                          Repositories / Services (данные, сеть) ← абстрагированы протоколами
```

- **View** — только отображение и жесты. Никакой бизнес-логики.
- **ViewModel** — состояние экрана и намерения пользователя. `@Observable`, `@MainActor`.
- **Domain** — чистые типы и правила (сделка, карточка, статусы). Не зависит ни от SwiftUI, ни от хранилища. Полностью тестируем.
- **Repositories / Services** — доступ к данным за протоколами, чтобы прототипную реализацию (локальное хранилище) можно было заменить сетевой, не трогая домен и UI.

---

## 3. Модель данных: три ортогональных примитива

Три первоклассных объекта. Они **не наследуются** друг от друга и живут в разных «домах».

### Message
- Единица разговора. Живёт в ленте конкретного чата, упорядочена во времени.
- Знает о карточке только по ссылке: держит `cardId`, но **не** её содержимое.

### Card
- Единица объекта в мире. Живёт в графе объектов **создателя**, существует независимо от любых переписок.
- **Живая ссылка**, а не копия: единый источник правды — объект в профиле автора. В чат уходит указатель + кэш-снимок (фото, название, цена на момент отправки) для офлайна.
- Полиморфна: `Товар / Услуга / Мастер` — это **разное поведение на общей оболочке**, а не разные сущности. Оболочка (фото, название, цена, описание) общая; поведение сменное.
- Card **не знает**, в скольких чатах её показывают.

### Deal (Сделка)
- Экземпляр взаимодействия «покупатель ↔ карточка». Одна карточка — много сделок.
- «Купить» и «Предложить цену» создают **один и тот же** объект Deal; разница только в стартовой цене и в том, нужен ли шаг «продавец принял».
- Когда сделке нужно решение человека — она **разворачивается в чат** с закреплённой карточкой. Так коммерция и общение сходятся в уже существующих примитивах.

**Правило хранения:** карточку никогда не храним внутри сообщения; сделку — внутри карточки. Связь только по ссылке (`id`). Отдельные хранилища. Тогда карточку можно показать в поиске и профиле, не трогая слой сообщений.

## 4. Прототип: границы реализации

- **Без платёжного слоя.** Пользователь — частное лицо без юрлица; держать чужие деньги (эскроу) он не вправе. «Купить» в прототипе = открыть чат с продавцом. Платёжный слой и безопасная сделка — отдельная фаза (см. [PRODUCT.md](PRODUCT.md)), появятся только с юрлицом.
- **Хранилище — локальное** (напр. SwiftData) за протоколами репозиториев; сеть добавляется позже без изменения домена и UI.
- **Контент для холодного старта** — посеянный вручную (прототип должен выглядеть живым).

---

## 5. Модульность

- Фиче-модули с чёткими границами: `Chats`, `Cards`, `Deals`, `Search`, `Content`, `Profile`.
- Общий домен и дизайн-система выносятся в отдельные модули (`DesignSystem`, `Core`).
- Зависимости — внутрь, к домену; наружу — только через протоколы. Каждый модуль собирается и тестируется отдельно.

---

## 6. Тестируемость

Любое решение должно быть легко тестируемым. Домен — чистые функции и типы, покрываются юнит-тестами без UI и сети. UI-логика изолирована во ViewModel и тестируется на моках репозиториев.
